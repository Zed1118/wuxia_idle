## 0. 执行摘要

当前生产版已经完成“透明全身战斗立绘 + 水墨人物舞台 + 武学案台”的结构迁移，方向没有走错，但实机仍明显停留在“可用的水墨战斗原型”，尚未达到基准图的成品装帧质量。

按本报告的统一评分模型，当前主线实机估分约为 **60/100**，与基准图仍有约 **40%** 的综合视觉差距。偏离并不平均分布：

- 总体左右阵列、旧纸配色和战斗功能骨架已达到约 70%～75%；
- 人物与场景融合度约 50%～60%；
- 武学案台的成品感约 45%～50%，是最大短板；
- 顶栏、血条、题字与局部高亮仍有较强的通用游戏 HUD 感。

本轮不重做战斗规则，不推翻已经终拍的 79+ 敌人立绘，不新增站位数值，不实现战斗药品规则。修复重点是：

1. 重标定顶栏、战场、案台的纵向比例；
2. 把 7 个技能槽从“程序矩形按钮”精修成真正的旧纸武学签；
3. 统一人物墨色、边缘、接地、尺度和 Boss 压迫感；
4. 让场景、人物、血条、题字、顶栏处于同一张水墨画卷中；
5. 建立可重复、可量化的 ≥85% 截图验收门槛。

若严格按本报告完成 P0、P1，预计可达到 **85～89 分**；完成全模式验收与差距收口后可稳定在 **90 分左右**，并减少不同关卡之间的风格波动。

## 1. 决策锁定

### 1.1 唯一风格基准

本轮以 V2 基准图作为唯一视觉母版。既有实现、旧截图、其他页面和单张角色原画只能作为素材来源或技术参考，不能反过来稀释母版风格。

基准图锁定以下内容：

- 横向水墨战场画卷的整体气质；
- 顶栏、战场、底部案台三段式结构；
- 左右人物的非对称纵深阵列；
- 暖灰旧纸、墨黑、暗金、绛红、低饱和青色的主色关系；
- 7 张竖向技能签和右侧 3 格战备行囊的视觉权重；
- 人物是第一视觉主体，案台是第二主体，HUD 退居辅助层；
- 细密、写实、克制的水墨武侠感，而非卡牌、页游或通用 Material 游戏界面。

基准图中的具体人物、招式名、血量、真气和道具数量仍是概念占位。生产实装必须读取真实数据，不能为了像素相似而伪造玩法状态。

### 1.2 还原目标的边界

“还原度 ≥85%”指的是同尺寸截图在以下方面达到高度一致：

- 构图比例；
- 视觉层级；
- 人物占屏与站位节奏；
- 材质、色相、明度和饱和度；
- 武学案台形态；
- 顶栏、血条、题字的时代感；
- 动态效果在定格帧中的风格一致性。

它不要求：

- 每一关使用同一张场景；
- 每个角色复刻基准图人物外貌；
- 所有技能签始终处于可用状态；
- 真实 1v1、2v2、Boss 战强行补齐为 3v3；
- 破坏可读性去追求纯像素差；
- 修改战斗数值、AI、tick、胜负、掉落或在线/离线规则。

### 1.3 本轮明确不做

- 不做实时 3D、骨骼动画或逐技能序列帧；
- 不新增前后排数值和“战斗开局站位倾向”；
- 不实现药品行囊自动补位；
- 不新增 Boss 技能预兆图标；
- 不把视觉整改扩成战斗公式或技能平衡改造；
- 不重新生成全部已终拍立绘；
- 不用高饱和金、紫、红制造手游稀有度光效；
- 不为 800×600 非正式小窗牺牲 1280×720 主构图。

## 2. 基线状态与风险

### 2.1 当前实机基线

本轮在 macOS 调试版进入正式主线“风雨渡口”取得 16:9 实机画面。可见状态为 3v1 首通战斗，具备：

- 我方祖师、大弟子、二弟子全身立绘；
- 敌方正式全身立绘；
- 主线水墨渡口背景；
- 顶栏战斗控制；
- 左侧执招者、中央 7 槽、右侧 3 行囊位；
- 首通“初战”题字；
- 贴身血条与真气条。

该画面足以判断全局风格和 1vBoss 自适应，但最终 85% 验收必须补一场标准 3v3，不能只用 3v1 代替人物阵列验收。

### 2.2 当前代码已经具备的基础

- `BattleLayoutTokens` 已集中管理顶栏、案台、人物尺寸和 Boss 缩放；
- `BattleField` 已支持 1v1、2v2、3v3、Boss、轻功、心魔与群战阵列；
- `BattleSceneBackground` 已有原画、远山、雾、地面、暗角和色彩分级；
- `BottomBar` 已固定 7 个技能槽和 3 个行囊位，无横向滚动；
- 技能签已有纸纹、竖排招式名、性质印、冷却和真气信息；
- 顶栏控制已经移出案台；
- 1280×720、1440×900 已有正式视觉路由和 widget 测试；
- 正式敌人透明全身立绘覆盖已经完成，不存在大规模缺图问题。

因此本轮属于“视觉标定与精修”，不属于重新搭战斗页。

### 2.3 基准资产状态风险

写报告时，基准图在工作区显示为已删除，但本轮开始时仍可正常读取；本报告没有执行删除，也不直接恢复，以免覆盖并发或用户操作。

实施前必须完成以下只做一次的基线确认：

1. 由主窗口确认该删除是否有意；
2. 若属误删，恢复与上述 SHA-256 完全一致的 Git blob；
3. 将基准图复制到视觉验收产物目录时保留原文件名和哈希；
4. 后续所有对照工具读取同一文件，不接受聊天截图、压缩预览或二次导出的替代品。

基准图缺失不阻碍本报告成立，但会阻断最终截图叠图验收。

## 3. 量化评分模型

### 3.1 总分构成

| 分项 | 权重 | 当前估分 | 目标最低分 | 核心判断 |
|---|---:|---:|---:|---|
| A. 构图与空间比例 | 20 | 15 | 17 | 三段比例、人物阵列、中央交锋区 |
| B. 人物美术与舞台融合 | 25 | 14 | 21 | 统一墨色、尺度、接地、Boss 压迫感 |
| C. 武学案台与技能签 | 25 | 12 | 22 | 竖签、材质、层级、空槽、行囊 |
| D. 色彩与材质统一 | 15 | 10 | 13 | 旧纸、墨黑、暗金、绛红、低彩青 |
| E. HUD、字体与信息层级 | 10 | 6 | 8 | 顶栏、血条、标签、字阶、时代感 |
| F. 动态效果风格一致性 | 5 | 3 | 4 | 题字、弹道、命中、闪光的克制程度 |
| **合计** | **100** | **60** | **85** | 任何 A～E 分项换算后不得低于 80% |

### 3.2 通过条件

同时满足以下条件才可宣称“还原度达到 85% 以上”：

1. 加权总分 ≥85；
2. A～E 每个分项自身得分率 ≥80%；
3. 1280×720 与 1440×900 均通过；
4. 标准 3v3、单 Boss、自动观战、允许点选四态均通过；
5. 无 overflow、人物关键轮廓遮挡、文字不可读或点击热区退化；
6. 用户对最终 3v3 与 Boss 对照图做一次视觉终拍。

### 3.3 不采用纯 SSIM 作为唯一门槛

生产截图与概念图的人物、关卡、招式和数值不同，直接做全屏像素相似度会错误惩罚真实内容。验收采用三层方法：

1. **结构量测**：区域比例、人物包围盒、案台宽度占比、元素对齐误差；
2. **感知量测**：明度、饱和度、主色占比、局部对比度、边缘密度；
3. **人工评分**：严格按本表逐项打分并附截图证据。

SSIM、感知哈希或图像差分只作为同一关卡改前/改后的回归辅助，不决定最终是否达到 85%。

### 3.4 A～F 子项评分规则

每个子项只能按“全部满足 / 部分满足 / 不满足”计分：

- 全部满足：拿满该子项分数；
- 部分满足：只拿该子项 50%，并必须写明差距；
- 不满足：0 分；
- 不允许用其他分项的超额表现补掉核心分项低于 80% 的失败。

| 分项 | 子项 | 分值 |
|---|---|---:|
| A 构图 | 顶栏/战场/案台纵向比例 | 5 |
|  | 执招者/7签/行囊横向比例 | 4 |
|  | 标准 3v3 非对称阵列 | 5 |
|  | 中央交锋区与 1v1/2v2/Boss 自适应 | 4 |
|  | 双视口稳定且无 overflow | 2 |
| B 人物 | 非透明包围盒光学尺度统一 | 6 |
|  | 六人接地与脚底墨影 | 5 |
|  | 黑位、饱和度、锐度、alpha 边缘统一 | 6 |
|  | Boss/主位/随从层级明确 | 5 |
|  | 脸、兵器、血条无遮挡 | 3 |
| C 案台 | 墨案整体轮廓和占屏重量 | 5 |
|  | 7 张旧纸技能签的材质与字阶 | 7 |
|  | 可用/冷却/气不足/待发/破招五态 | 5 |
|  | 执招者名帖与当前角色层级 | 4 |
|  | 行囊木匣、器物格和空态 | 4 |
| D 材质 | 总色板和低饱和关系 | 5 |
|  | 场景/人物/案台纸墨材质一致 | 5 |
|  | 不同场景 profile 稳定 | 3 |
|  | 高饱和语义色面积受控 | 2 |
| E HUD | 战斗专用字阶与跨平台字体 | 3 |
|  | 顶栏题签化与控制层级 | 2 |
|  | 血条、真气、状态板旧纸化 | 3 |
|  | 对比度、最小字号和桌面语义 | 2 |
| F 动态 | 首通/破招/大招题字统一 | 2 |
|  | 动作、弹道、命中和收势风格统一 | 2 |
|  | 快进/减少闪烁状态仍可读 | 1 |

以下任一项失败时，总分最高只能记 84，不能宣称达标：

- 基准图缺失或哈希不一致；
- 任一正式视口 overflow；
- 关键人物脸部、主要兵器或血条被遮；
- 核心按钮丢失 semantics、键盘激活、focus 或 mouse cursor；
- 为截图伪造生产数据或改变战斗规则；
- 只提交 debug fixture，没有正式 `BattleScreen` 生产接线证据。

评分顺序固定为：实现者自评 → Codex 按同表复核 → 用户只对最终 3v3/Boss 主对照图终拍。出现争议时以基准图、结构量测和用户终拍为最终裁决，不取多人平均掩盖明显偏离。

### 3.5 可复现的量测定义

- **截图范围**：只比较 Flutter 游戏内容区，排除 macOS/Windows 标题栏、窗口阴影、桌面和鼠标指针；
- **逻辑尺寸**：以 Flutter logical pixels 为准。Retina 2× 截图先精确缩回 1× 再量测；系统缩放和 DPR 记录在 manifest；
- **跨尺寸对齐**：基准图按 16:9 内容区等比 `cover` 到目标逻辑尺寸，再从中心裁切，不拉伸；结构比例全部用 0～1 归一化坐标；
- **人物包围盒**：使用立绘层 alpha >16/255 的最小外接矩形，包含兵器和衣摆，排除脚底影、题字、受击闪、弹道与其他特效；
- **Boss 面积比**：Boss 外接矩形面积 ÷ 同一截图中三名非 Boss 我方人物外接矩形面积中位数；通过线 ≥1.25，目标带 1.25～1.45；
- **接地误差**：立绘 alpha 包围盒脚底与该槽地面锚点的垂直误差 ≤人物视觉高度的 2%；
- **语义色面积**：在 UI/特效诊断层中按 HSV `S≥0.55 且 V≥0.45` 统计，排除原始人物和背景资产；非大招帧占内容区 ≤8%；
- **黑位漂移**：同一人物跨三种代表背景，人物 mask 内 5% 暗部分位的相对亮度差 ≤0.05；
- **正文对比度**：小字与直接底色至少 4.5:1，大字/粗体至少 3:1；装饰性墨纹不计正文；
- **5 秒识别**：在 100% 逻辑缩放、约 60cm 观看距离下，观察者需在 5 秒内指出敌我、人数、Boss、当前角色和可破招签；任何一项错误则该检查失败；
- **“不抢眼”判据**：灰阶缩略到 50% 时，除人物脸部和当前技能签外，不应有连续六块以上高对比矩形成为第一视觉中心。

量测工具可使用现有截图脚本与后续只读分析脚本；若新增分析脚本，必须把阈值写入单一配置并输出原始 mask/JSON，禁止只输出一个无法复核的总分。

## 4. 基准图视觉拆解

### 4.1 纵向比例

以 1672×941 基准图归一化：

| 区域 | 目标占屏 | 允许误差 |
|---|---:|---:|
| 顶栏 | 约 6%～7% | ±1% |
| 主战场 | 约 67%～69% | ±2% |
| 武学案台 | 约 24%～26% | ±2% |

案台不能因为自动模式收成一条普通工具栏。自动模式可以降低交互强调，但必须保留“完整武学卷案”的视觉重量。

### 4.2 横向比例

案台内部目标：

| 区域 | 目标占案台宽度 | 允许误差 |
|---|---:|---:|
| 执招者 | 18%～20% | ±2% |
| 7 张技能签 | 58%～62% | ±2% |
| 战备行囊 | 20%～22% | ±2% |

中央技能谱必须是案台第一主体。当前实现的固定 222px 左右栏在不同窗口上容易让中区视觉重量不足，需改成“比例为主、上下限为辅”的响应式 token。

### 4.3 人物阵列

标准 3v3 的目标不是镜像三列，而是左右各自形成斜向纵深：

- 我方祖师处于外侧前景，尺度最大或与主位相当；
- 两名弟子向中场与后景错位；
- 敌方主位明显前压，随从退向右后方；
- 人物允许少量轮廓重叠，但脸、兵器、血条不得被遮；
- 中央保留约 20%～28% 的交锋与特效空间；
- 单 Boss 应比普通角色视觉面积大 25%～45%。

现有 `bossStageScale = 1.22` 只达到理论下沿，而且会被不同资产自身透明边距、人物包围盒和姿态抵消。最终必须按“非透明人物包围盒视觉面积”验收，不能只检查 Widget scale 数字。

### 4.4 明度和色彩关系

基准图的色彩优先级：

1. 墨黑和暖灰承担约 70%～80% 画面；
2. 旧纸黄承担约 15%～20%；
3. 绛红、暗金、青灰等语义色合计不超过约 8%；
4. 任一高饱和纯色都不能形成大面积视觉中心；
5. 敌我差异主要靠站位、朝向和名字，不靠蓝队/红队涂色。

## 5. 分区问题与修复要求

### 5.1 P0：武学案台

#### 当前问题

- 案台整体仍像贯穿全宽的深色矩形工具栏；
- 技能槽外形规整、平直、重复，程序按钮感强；
- 空技能位使用大块浅纸 + 竖排“空技能位”，占据过多注意力；
- 技能签的招式名、印章、真气、冷却虽然都有，但字阶差异不够；
- 左右分区是方框面板，缺少案、卷、匣的器物关系；
- 自动模式视觉压缩过度，无法保持基准图的案台重量；
- 行囊素材存在，但格子像普通 inventory slot，缺少木匣和织物质感。

#### 修复目标

1. 案台底层改为“下缘墨案 + 局部纸签”，不要只靠一整块纯深色 Container；
2. 7 张技能签固定可见，签宽一致，签高可有 2%～4% 的自然错落；
3. 每张签至少具备：旧纸底、内墨线、局部毛边、顶部招名、性质印、底部气脉；
4. 可用态使用纸色与墨字，不可用态用墨层覆盖，不得变成 Material disabled 灰按钮；
5. 冷却用墨色由上至下浸染，并保留数字；
6. 可破招只使用一次克制的暗金描边或抬签，不持续高亮闪烁；
7. 空槽改为淡墨留白签：保留边线与小型空印，主文字透明度降低至不抢招式签；
8. 左侧执招者改成书页签/名帖层级，当前人物展开，其他两人收束；
9. 右侧行囊改为木匣或旧锦格，器物图不与技能签同形；
10. 自动观战时保留完整案台高度，只降低按钮感和交互描边。

#### 建议实现落点

- `battle_layout_tokens.dart`：案台高度、左右分区比例、技能签尺寸；
- `battle_bottom_bar.dart`：底层案台、`SkillCommandButton`、`EmptySkillSlot`、`FocusSelector`、`BattlePouchRail`；
- `wuxia_tokens.dart`：新增统一案台色、墨边和材质 token；
- `assets/ui/`：如现有纸纹不足，补一套可九宫格缩放的签纸边、木匣边和墨案边，不新增大运行时依赖。

#### 验收门槛

- 案台占屏高度 24%～26%；
- 中央 7 签占案台宽度 58%～62%；
- 5 秒内能指出当前角色、可用招式、可破招、真气不足、冷却；
- 截图第一眼不得读成七个普通 ElevatedButton；
- 空槽存在时仍像未题字的武学签，而非开发占位卡。

### 5.2 P0：人物立绘与舞台融合

#### 当前问题

- 不同立绘的黑位、纸色残留、锐度和颗粒存在差异；
- 人物脚底接地较弱，部分角色像悬浮在场景上；
- 立绘边缘过干净或过锐，与背景水墨笔触分离；
- 相同 scale token 对不同透明边距资产产生不同视觉大小；
- Boss 仅按 Widget 比例放大，真实包围盒压迫感不足；
- 人物名牌和资源条使用硬黑矩形，切断人物与场景。

#### 修复目标

1. 保留已终拍立绘原画，不做全量重生成；
2. 为战斗立绘增加统一的只作用于表现层的色彩校准：低饱和、暖灰黑位、压高光；
3. 统一 alpha 边缘去白边/黑边规则；
4. 增加脚底淡墨接地影，方向和透明度随场景统一；
5. 使用非透明包围盒校准人物“光学高度”，已有校准映射继续作为真相源；
6. Boss 以视觉面积而非原图画布尺寸校准，统一按 §3.5 的“Boss ÷ 三名非 Boss 我方人物面积中位数”计算，目标比值 1.25～1.45；
7. 人物信息板改为半透明墨拓底，缩短黑底宽度并降低阴影；
8. 姓名、HP、真气贴近人物但不得覆盖腿、武器或脸；
9. 阵亡态做褪墨和下沉，不留下完整灰色剪纸。

#### 验收门槛

- 任意标准 3v3 中六人脚底均落在合理地面带；
- 角色间光学头身尺度差只来自设定，不来自透明边距；
- Boss 非透明包围盒面积比按 §3.5 唯一算法计算，至少达到 1.25；
- 缩略到 50% 观看时，人物与场景仍像同一张画，不像贴纸拼贴；
- 玩家已终拍的立绘内容和角色辨识度不被滤镜破坏。

### 5.3 P0：战场构图与背景层次

#### 当前问题

- 正式背景已经是水墨原画，但中景与人物接触层较平；
- 中央大面积纸灰留白有利于特效，却缺少基准图的雾、地面、树石层次；
- 不同场景色彩分级强度不一致，容易出现人物暖、背景冷或反之；
- 暗角和 40% 黑色 scrim 在部分亮背景上有效，在暗背景上可能把细节压死。

#### 修复目标

1. 保留每关独立场景，不强行复用基准图山道；
2. 场景必须同时具备远景、中景、地面接触层和前景压边四层；
3. 中央交锋区保留低细节，不保留纯空白；
4. 背景压暗改为按场景 profile 配置，不全局固定 40%；
5. 主线、塔、心魔、轻功、群战分别有受控色彩 profile，但都服从总色板；
6. 人物脚底附近增加轻微雾切和墨地，帮助接地；
7. 前景装饰只压边，不遮挡人物关键轮廓和点击区域。

#### 验收门槛

- 灰阶截图中仍能看出远、中、近景层次；
- 中央交锋区与两侧人物区的边缘密度差异明确；
- 背景不能比人物脸部和技能签更抢眼；
- 同一人物在三类背景上不出现明显贴图感或黑位漂移。

### 5.4 P1：顶栏与战斗控制

#### 当前问题

- 当前圆形 IconButton 和 pill 较像通用桌面应用；
- 控件尺寸偏小，基准图则是带题签感的文字控制；
- 场景标题、战斗人数和控制组层级差距不足；
- 顶栏高度约束更接近 8%，基准目标约 6%～7%。

#### 修复目标

1. 顶栏高度收敛至视口 6%～7%，1280×720 下仍保证点击区 ≥36px；
2. 核心控制使用“自动 / 一倍 / 暂停 / 日志 / 撤退”短文字或字+极简图标；
3. 控件外形改为墨边圆牌/窄题签，弱化 Material 圆形按钮；
4. 中央“战斗 3 v 3”保持最大字号；
5. 左侧场景题名次之，节拍再降一级；
6. 右侧控制保持等距，不使用高亮实心色块；
7. 帮助入口进一步弱化，不与战斗控制争夺注意力。

#### 验收门槛

- 顶栏高度和基准图误差 ≤1 个百分点；
- 1280×720 下所有控件可键盘聚焦、鼠标悬停、语义可读；
- 截图中顶栏不能比人物和技能签更抢眼；
- 控件第一印象是武侠题签，不是 Material toolbar。

### 5.5 P1：血条、真气与状态信息板

#### 当前问题

- 黑色长方形底、纯红 HP 和青色气条对比过硬；
- 信息板阴影较重，像浮在人物脚边的现代 HUD；
- 3v3 下名字和数值容易缩得过小；
- 当前资源条与基准图接近，但缺少旧纸/墨拓连接。

#### 修复目标

1. 底板改为窄墨拓或暗纸条，避免纯黑发光框；
2. HP 用深绛红，真气用低饱和青灰；
3. 轨道底色改为暖墨灰，不使用中性 UI 灰；
4. 名字优先于精确数值，低视口允许数值缩写但不可失去语义；
5. 常驻只显示名字、HP、真气和最多两个关键状态；
6. Boss 标签使用暗金/绛红小印，不使用大面积金框。

#### 验收门槛

- 1280×720 下名字最小可读；
- 灰阶下 HP 与真气仍可通过位置、长度和纹理区分；
- 信息板不遮挡脚、武器和相邻人物；
- 画面缩小后信息板不形成六块醒目的黑砖。

### 5.6 P1：字体、印章与文案排版

#### 当前问题

- 已使用宋体/楷体 fallback，但不同区域字重和字距缺少统一阶梯；
- 小字号过多，导致实机像“把信息塞进去”；
- 印章存在但视觉尺度偏小，性质识别弱；
- 数字和中文的字面高度不统一。

#### 修复目标

建立战斗专用字阶，不在各 Widget 继续散写：

| 层级 | 用途 | 建议视觉字号 |
|---|---|---:|
| T1 | 战斗人数 / 大招题字 | 24～32 / 动态另计 |
| T2 | 场景标题 / 招式名 | 15～20 |
| T3 | 人物名 / 案台区名 | 11～14 |
| T4 | 真气、冷却、节拍 | 9～11 |
| T5 | 辅助提示 | 最低 9，且需足够对比度 |

补充要求：

- 招式名最多 4 字竖排，超过 4 字需数据层短名或稳定排版方案，不能静默截成难懂词；
- 性质印使用绛红或暗墨，尺寸足以在 1280×720 识别；
- 数字使用统一 tabular figures 或等宽策略，避免血量跳动；
- 字体选择必须兼顾 Windows 发布目标，不依赖 macOS 独占字体表现。

### 5.7 P1：题字、命中和高亮效果

#### 当前问题

- “初战”使用大面积亮黄色墨爆，是实机中最偏离基准色板的元素；
- 暴击金 `#FFD700`、结果高亮和部分英雄镜头可能过亮；
- 大招题字、首通题字、破招题字各自可读，但未完全共享同一套旧墨规则；
- 高亮容易依赖发光，而基准图依赖暗金边、纸张和墨迹。

#### 修复目标

1. “初战”改为旧金/绛红题签或墨章，不使用大面积鲜黄爆点；
2. 暴击金压到旧金色域，峰值可亮但持续时间必须短；
3. 题字统一纸墨边缘、颗粒、入场/消散曲线；
4. 敌方危险以绛红墨痕和局部压暗表达；
5. 我方可用/破招以暗金抬签表达，不用持续 glow；
6. 特效透明度和面积按普攻、强力、大招三级约束；
7. 减少闪烁设置下仍能通过形状和位移读懂动作。

#### 验收门槛

- 任一非大招帧，语义色面积不超过全屏约 8%；
- 大招峰值后 300～500ms 内恢复低彩画面；
- “初战”定格帧不再成为全屏唯一高饱和焦点；
- 自动快进时无彩色特效长期堆积。

## 6. 统一资产与后处理规范

### 6.1 立绘保留策略

所有已终拍正式立绘默认保留。按以下顺序处理：

- 无明显白边、黑边、压缩脏边；
- 脚底基线明确；
- 头顶、兵器、衣摆保留安全区；

- 黑位不糊死，肤色不突兀；

- 50% 缩放仍能辨认兵器和体型。

### 6.3 新增 UI 资产限制

允许新增：

- 可九宫格缩放的技能签毛边；
- 墨案下缘；
- 木匣/旧锦行囊框；
- 淡墨接地影；
- 统一印章底纹。

不允许新增：

- 大面积不可缩放整屏 UI 图；
- 每个技能独立按钮底图；
- 高饱和稀有度边框；
- 需要额外游戏引擎或大体量运行时的资产系统。

## 8. 测试与视觉证据要求

### 8.1 自动化测试

至少覆盖：

- 7 技能槽与 3 行囊位始终存在；
- 双视口无 overflow；
- 自动/点选案台高度符合 token；
- 空槽、冷却、气不足、破招、待发状态可定位；

- Boss scale 与光学包围盒规则；
- 减少闪烁和快进路径不改变输入语义；
- 视觉 token 不在多个 Widget 散写。

### 8.2 截图证据矩阵

每个视口至少交付以下截图：

| 编号 | 场景 | 必看内容 |
|---|---|---|
| S1 | 标准 3v3 静态 | 六人阵列、案台全貌 |
| S2 | 单 Boss 静态 | Boss 尺度、中央留白 |

| S9 | 大招峰值 | 人物主体、低彩恢复 |

| S11 | 快进多特效 | 无长期彩色堆积、飘字不撞 |

- **四个核心状态**：标准 3v3、单 Boss、自动观战、允许点选；

## 10. 风险与防回退

### R1：只修一张关卡截图

防线：标准 3v3 + 单 Boss + 塔 Boss + 四种交互状态共同验收。

### R2：为还原样图牺牲信息可读性

防线：85 分评分中 HUD 和交互是独立硬门槛；不允许用纯图层盖住真实信息。

### R3：滤镜统一导致角色辨识度下降

防线：运行时后处理先做代表样板，逐张抽验肤色、兵器和服装；不批量覆盖原资产。

### R4：空技能位持续呈现半成品

防线：空槽本身作为正式视觉状态验收，不以“以后玩家会装满”为理由跳过。

### R5：Boss scale 数字通过但视觉仍小

防线：改用非透明包围盒面积比作为最终判据。

### R6：macOS 字体通过、Windows 失真

防线：字体 fallback 和字面高度进入 token；“D 段”明确指 ship 前 Windows 发布实机验证。Mac 端 85% 门槛通过后，Windows 至少在 1920×1080 的 100%/125%/150% 系统缩放各验一次标准 3v3 与 Boss；字体必须来自项目打包字体或 Windows 可验证 fallback，不宣称 macOS 可替代发布平台终验。

### R7：视觉证据随 worktree 清理丢失

防线：最终拍板三联图复制到主 checkout 的稳定证据目录或文档引用位置；清 worktree 前先核对证据存在。

### R8：外部审查意见直接变任务

防线：任何新问题先对照实机、基准图和本评分表证伪，再决定是否进入修复切片。
