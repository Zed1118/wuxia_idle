## 0. 为什么需要这份 spec

路线 C 的硬前提清单里有「Phase 1 纵切成立」,但截至起草日**全库无定义**——GDD/CLAUDE/派单档均只引用不定义。无定义则第三序(0A 主线接线 + 旧入口原子拆除)永远无法判定「前提满足」。本 spec 给出定义、范围候选与成立判据,拍板后入 GDD §7.4 执行批口径。

## 1. 定义(提案)

**Phase 1 纵切 = 用 0A 形态跑通一段真实生产内容的全链路**,证明新引擎承载的是「游戏」而非「可玩样片」。全链路 = 内容定义 → 装配 → 表现 → 结算 → 奖励 → 进度保存 → 可重复进入(headless 复核)。

与既有阶段的界线:
- Phase 0A = 灰盒玩法闭环(自造 fixture,不消费生产内容);
- Phase 0B = 美术样片(连续地图方向锁定,无玩法接线);
- **Phase 1 = 首次让生产内容(真实 yaml 关卡/敌人/奖励)经 0A 引擎被玩家消费。**

## 2. 范围候选(拍板点 P1)

| 选项 | 内容切片 | 覆盖面 | 工作量 |
|---|---|---|---|
| α 主线一章(推荐) | Ch1 五关(stage_01_01..05)全链 | 主线=核心体验;叙事/奖励/进度/首通语义全触达 | 中 |
| β 塔一段 | 塔 1-7 层 | 触周目/境界门槛语义,但叙事面窄 | 中 |
| γ 断魂庄一路 | boss_gauntlets 单路 | 触托管 headless 语义,但属支线 | 小 |

**推荐 α 的理由**:主线是旧 3v3 拆除后玩家第一时间面对的内容;Ch1 数值最浅,适配摩擦最小;主线进度服务(mainline_progress_service)是 headless 结算链消费方之一,α 天然验证其新引擎兼容性。

## 3. 构成层(α 案展开)

1. **内容映射层**:stage yaml → 0A 波次/遭遇装配。决策点见姊妹篇决策单 D1(敌队如何从 3v3 六人队伍映射为怪海波次)。
2. **表现层**:0A 战斗屏(Batch 1-9C 已合)承载;连续地图(0B 方向)是否并入 Phase 1 为拍板点 P2——**推荐不并入**(0B 正式拆层资产尚缺,先以竞技场形态完成纵切,连续地图留 Phase 1.5)。
3. **结算层**:live = 0A 可玩 flow;headless = `Phase0aHeadlessRunner`(2026-08-19 已合,bot 全程驾驶)。**双跑一致性**为成立判据之一:同一初态+同一 seed,live 与 headless 终局必须一致。
4. **进度层**:通关写回 mainline_progress_service;离线挂机主循环不经战斗引擎(N1 §3.2 实测),本层零改动即兼容。

## 4. 成立判据(提案,逐条可验)

- [ ] Ch1 五关可由真人从主线入口进入并通关(或战败重试),存档进度正确写回;
- [ ] 每一关 bot headless 双跑结果与 live 结算一致(胜负 + 关键数值);
- [ ] 战败/重试/中途退出零存档污染(0C 静态守卫体例);
- [ ] 离线挂机收益在纵切期间零回归(挂机主循环不经引擎,以全量测试托底);
- [ ] Mac 本机帧时间达标(沿用 0C 口径:reducer + 表现层合计不吞帧预算;正式 Windows 数据留实机 Gate)。

## 5. 非目标(本 spec 明确不做)

- 不做原子切换(第三序=0A 主线接线批 + 旧入口拆除批同次 merge,拍板④);
- 不删旧屏/旧路由(enum 条目随表现层拆除批删,拍板②);
- 不改远征/断魂庄/扫荡的消费面(绑内容迁移 ADR,见姊妹篇);
- 不做连续地图正式拆层资产(0B 手动 rig 仍 pending)。

## 6. 依赖与顺序

Phase 1 纵切的执行前提 = 本文档拍板 + 姊妹篇决策单至少 D1(内容映射)拍板;
纵切「成立」后,路线 C 硬前提清单只剩 6 人 Gate + Windows 实机(用户排期项)。
