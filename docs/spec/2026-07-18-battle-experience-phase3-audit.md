# 战斗体验三期：界面、特效与战斗方式审计

> 日期：2026-07-18  
> 阶段：1.0 长线打磨期  
> 基线：`main@f41cb556`  
> 状态：今晚目标已确定，首切片已完成并验证

## 1. 结论

战斗界面已经完成“水墨人物舞台 + 武学案台”重构，正式敌人透明全身立绘覆盖也已达到 79/79。三期不再重做页面结构，而是解决三类真实体验断点：

1. **动作语义与特效交付不一致**：远程大招被 `cinematic` 提前截断，保留题字与重击反馈，却没有从施术者连向目标的弹道。
2. **自动观战与点选干预的表现差异仍偏弱**：现有生产链路功能完整，但自动模式更像“不能点的同一张案台”，后续应把轮转与观察价值表达清楚。
3. **战斗方式优化缺少量化入口**：不直接改公式或加新站位数值，先测量真气就绪、破招窗口、手动插队频率和三人出手分布，再判断应优化节奏、信息还是规则。

今晚首切片选择第 1 项。它同时影响人物动作、远程特效和招式辨识，改动局限于表现层，收益高且不触碰战斗结算。

## 2. 现状证据

### 2.1 已成立的基线

- `BattleScreen` 已生产接入全人物舞台、7 槽武学案台、3 格战备行囊预留位。
- 1280×720 与 1440×900 是正式桌面验收视口；本次在 1280×720 实机复核无 overflow。
- `battle_tap_live`、正式关卡与 70 条战斗视觉路由可直达验收。
- 五类动作模板、弹道、流派命中特效、飘字、受击闪、屏震、大招题字和首通展示帧均已存在。
- 单体两段点选、唯一目标直放、群体直放、长按说明、ESC/空白取消均保持现状，不恢复拖放。

### 2.2 已证伪的问题

视觉路由不设置 `VISUAL_WINDOW_W/H` 时会按原生默认窗口落到约 800×600，技能签头部产生 3.8px 横向 overflow。正式最低窗口档是 1280×720，锁定该视口后不复现，因此本期不把它列为产品缺陷，也不为未支持的小窗牺牲 720p 构图。

### 2.3 已确认的问题

`battleActionTemplateFor` 当前顺序为：群攻 → 控制 → 大招/共鸣 → 远程标记 → 近战。于是所有单体大招先命中 `cinematic`，`glow_sword`、`wind_slash`、`flying_sword_art`、`qi_*` 等远程标记永远无法进入 `projectile`。

大招题字、重击分档、专属 SFX 和命中特效均由技能类型独立触发，不依赖 `cinematic` 枚举。因此让明确远程的大招使用 `projectile` 交付，不会丢失大招仪式感，只会补回缺失的施术者→目标联系。

## 3. 三期优化路线

### P1：动作与特效语义正确

- 远程大招保留大招题字/重击/SFX，同时生成远程弹道且人物不冲到交锋点。
- 后续审计群攻是否因逐目标 action 重复叠加同一中心特效；若成立，做同拍去重而不吞目标受击反馈。
- 后续把“人物站位动作”和“招式交付方式”拆成正交画像，避免一个枚举继续承担两个维度。

### P1：自动与点选干预的界面分工

- 自动模式强调当前轮转、真气与冷却观察，不把技能签处理成普通 disabled 按钮。
- 点选模式继续突出执招者、待发招式和合法目标的连续引导。
- 不新增教程弹窗；用案台状态、题签和一次性战斗反馈表达。

### P2：战斗方式优化先探针后改规则

- 统计代表性主线/Boss 战中的三人出手占比、技能占比、真气溢出/不足、可破招窗口和手动插队可用率。
- 若问题是信息不可读，优先改表现；若问题是选择长期无价值，再提交独立 balance 方案。
- 不引入站位攻防数值、传统体力、在线手动优势或新的成长阶级。

## 4. 今晚阶段目标

1. 建立本审计与可恢复计划。
2. 用失败测试证明远程大招当前被错误分类。
3. 修正动作分类优先级，并验证控制、群攻、近战和普通远程无回归。
4. 在播放控制器层证明远程大招会生成弹道，且仍走既有大招题字/重击路径。
5. 运行相关 targeted tests、`flutter analyze --no-pub`，并做 1280×720 / 1440×900 战斗视觉 smoke。
