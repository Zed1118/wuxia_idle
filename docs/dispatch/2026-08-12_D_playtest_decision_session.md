## 一、任务背景(自包含,执行端无本方上下文)

本仓是 Flutter Desktop 写实武侠挂机游戏,长期由 AI 协作推进。2026-08-11 做过一次阶段性评估,结论是**工程执行面 9.5/10、流程面 4.5/10**,最大瓶颈写得很直白:**决策积压**——有一批事情卡在"没有人真正坐下来玩过 / 看过真机",AI 再怎么量测也拍不了板。

这类问题的共性是「好不好看 / 好不好玩只有人能定,量测只能排硬伤」。它们已经在储备账 `BACKLOG.md` 里挂了很久,有的续传了三轮。

**本单的产出目标**:让项目主人**一次坐下(约 30-60 分钟)就能把这批决策一口气清掉**。产出两样东西:

1. 一份**决策局清单**(md):每项决策要看什么、在哪看、有哪几个选项、已有什么证据、拍完之后会改动什么
2. 一个**启动脚本**(shell):按清单顺序把该看的东西依次推到人眼前,人只需要看和答

**你不是来替他做决定的**。你是来把「他要做决定所需的一切」准备到位,让他不必自己去翻仓库、找证据、想选项。

## 三、产出一:决策局清单

落盘 `docs/spec/2026-08-12-playtest-decision-session.md`。

**每一项决策一节**,每节必须含以下五块(缺一不可):

1. **要定什么** —— 一句话,人话,不要抄技术描述
2. **看哪里 / 玩哪段** —— 具体到可执行:哪条视觉路由 id、哪个图片文件绝对路径、游戏里从哪进哪个界面、要玩到什么程度才够判断
3. **选项** —— 逐个列全,每个选项一句话后果。**已有的选项照抄不要自己发明**(如一#17 原文已有 abcd 四项);原文没列选项的(如一#19 只给了"色阶/印章/边框/底纹"四个方向),整理成可勾选的形式
4. **已有证据** —— 把已经做过的量测/实测结论压缩成 2-4 行,附证据文件路径。目的是让人不必重新验证一遍,也避免他去重复做 AI 已经做完的活
5. **拍完之后** —— 这个决定一旦拍下,会改动哪些文件/哪个常量/哪条记录;是否需要另开实装任务

**排序要求**:按「同类连着看」排,不要在美术和数值之间来回跳(切换成本高)。建议顺序 = A 组(视觉,连着看完)→ B 组(玩)→ C 组(桌面,最后清)。**A 组内部**再按"同一屏能一起看的排一起"。

**顶部加一张一页速览表**:编号 / 一句话 / 组别 / 预计耗时。让人一眼知道这局要花多久、能清掉几项。

**时间预算**:每项标注预估耗时,总和写在速览表下方。若你算出来总和明显超过 60 分钟,**如实写出来并给出"最少必做"子集建议**——不要为了凑"一局清完"把时间估小。

## 四、产出二:启动脚本

落盘 `tools/playtest/decision_session.sh`(目录不存在就建)。

**要求**:

1. **分步、可中断、可从任意步继续**。人在中间被打断是常态。建议形态:`./decision_session.sh` 列出步骤;`./decision_session.sh <step>` 直接跳到某步。
2. **A 组视觉项**:用仓里既有的视觉路由机制把界面推到人眼前。**真实路由 id(派单方已实测,直接用)**:
   - 一#19 资质 chip → `lineage_character_detail`
   - 二#7 立绘融合 → `battle_v2_neutral_3v3`(另可参考 `battle_scene`)
   - 一#17 桃花岛背景 → 该项是图片取舍,先用系统 `open` 打开候选图与两张复检对照图;**若仓里存在能进入桃花岛场景的路由**,一并给出(自己去 `lib/features/debug/application/visual_route.dart` 现查,查不到就如实写"无现成路由,需游戏内自行进入"——不要编一个不存在的 route id)
   - 视觉路由的启动方式去 `tools/visual_capture/visual_capture.sh` 与 `lib/features/debug/` 现读,照仓里既有体例,不要自创
3. **B 组玩的项**:脚本能做的只有"把游戏启起来 + 打印该玩哪段、看什么指标"。**不要试图自动化试玩**。
4. **C 组桌面项**:脚本打印出决策所需的事实(如 P12 的四个分支各自 `main..origin/<b>` 现算独有 commit 数——**现算,不要抄 BACKLOG 里的旧数**),人直接答。
5. **脚本必须先自检环境**:`DEVELOPER_DIR` 若被设置会导致 `flutter build macos` 报 `xcrun: unable to find utility "xcodebuild"`,脚本开头要检测并 `unset` 或明确提示。这是本仓踩过多次的坑。
6. **脚本不许自动修改任何东西**——只负责"把东西推到人眼前"和"打印事实"。所有落笔由人拍板后另行实施。
7. 脚本要有 `--dry-run`,只打印每步会做什么而不真的启动 app。**交付前你必须用 `--dry-run` 跑一遍并把输出贴进交付说明**。

## 五、验收标准

1. 两份产出都已 commit。
2. **清单里每一条"看哪里/玩哪段"都必须是你现查过的真实路径/路由/入口**。凡是你没能核实的,写"未核实"并说明,**不许写一个看起来合理但没查过的路径**——这是本单最容易出假货的地方,派单方会逐条抽查。
3. `decision_session.sh --dry-run` 实跑输出贴进交付说明。
4. `shellcheck` 若本机可用则跑一遍并贴结果;不可用则说明。
5. 交付说明里明确回答:**8 项是否全部覆盖**;若有某项你判断"证据不足以让人当场拍板",如实说出来并写清还缺什么。

## 六、边界约束(硬)

- **禁区文件,一个都不许碰**:`data/numbers.yaml`、`GDD.md`、`PROGRESS.md`、`lib/shared/strings.dart`、`pubspec.yaml`
- **不许改 `lib/` 下任何 `.dart`**、不许改任何 `data/` 下的 yaml、不许改任何美术资产。本单是**备局**,不是实装。
- **不许替用户做决定**。清单里不要出现"建议选 b"这类倾向性结论——你可以陈述量测事实,但**取舍留白**。(唯一例外:§三 第 5 块"拍完之后"里陈述客观后果不算倾向)
- **不许跑 `flutter build macos` / 视觉截图脚本去"验证脚本能用"**。用 `--dry-run` 验证;真机实跑是用户那一局的事。
- **不许把 BACKLOG 里的旧数字当现值抄进产出**。凡数字,要么现算,要么标注"截至 <日期> 的登记值,未复算"。
- **禁 push、禁 merge、禁碰 main、禁 revert**。
- commit message 用**中文动宾**结构(英文 conventional 前缀属违规)。
- 交付时工作区干净,分支 **tip commit 消息以 `[READY]` 开头**。
