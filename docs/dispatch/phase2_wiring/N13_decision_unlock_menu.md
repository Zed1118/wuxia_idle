# N13 · 二阶段拍板菜单(按解锁力排序)

## 背景

N12 已把《二阶段优化方案》的遗留工作转成 39 条任务池条目(`docs/dispatch/pool/phase2_leftover_pool_proposal.md`,
本 worktree 内,基线 `f1e645f0`)。实测分布:

- 🟢 已解锁可派 7 条 / 25 组
- 🟡 先出方案 1 条 / 1 组
- 🔴 待用户拍板 31 条 / **210 组(占 236 组的 89.0%)**

结论是**瓶颈在签字不在产能**。因此本单的产物不是又一份审计,而是一份**用户早上可以直接逐条勾选的拍板菜单**,
按「签这一条能解锁多少工作」排序。

## 目标

产出 `docs/dispatch/pool/phase2_decision_menu.md`,回答一个问题:
**用户接下来该先拍哪几条,才能用最少的决策解锁最多的工作。**

## 方法

### 步骤 1 · 建依赖图

从池文件两张表逐行取 `前置依赖` 列。把依赖项分成三类,**分类必须逐条给出判据**:

- **S 类(用户签字)**——需要用户拍板才能动,例:「C01 重新拍板装配方案数量」。
- **G 类(用户体验签字)**——需要真人试玩/主观认可,例:「G2 试玩通过」。§18 M2 Gate 有八项试玩签字表。
- **E 类(工程前置)**——另一条任务做完即可,不需要用户,例:「A03、A05 合同关闭」。

### 步骤 2 · 算解锁力

对每个 S 类与 G 类节点算三个数:

| 指标 | 定义 |
|---|---|
| 直接解锁组数 | 该决策自身承载的组数 |
| 传递解锁组数 | 沿 `前置依赖` 边可达、且除此之外无其他未满足 S/G 前置的条目的组数之和 |
| 总解锁组数 | 上两者之和,**不得重复计数同一组** |

**守恒硬约束**:所有 S/G 节点的「总解锁组数」在去重后 **≤ 236**。
产物里必须显式贴出这次去重后的合计数与 236 的差额,并解释差额来自哪些条目(如 🟢 本就无需解锁)。

### 步骤 3 · 出菜单

按总解锁组数降序,逐条给出:

| 字段 | 要求 |
|---|---|
| 决策 ID | 用方案 §0.2 已有的决策 ID(如 `INNER-DEMON-CULTIVATION-01`)。方案没有 ID 的写「方案未编 ID」,**禁止自造 ID** |
| 一句话问题 | 用户要拍的到底是什么,用大白话,不用黑话 |
| 当前状态 | `FROZEN` / `PROPOSED` / `TUNING` / 查无实据 —— 必须给出处行号 |
| 可选项 | **只列方案原文已经写出的选项**。方案没列选项的,写「方案未列选项,需用户先定方向」——**禁止自己发明选项** |
| 拍板需要看什么 | 用户要做这个决定需要先看到的证据(某份测试结果 / 某个画面 / 某段数值),给具体路径或「尚不存在,需先产出」 |
| 直接解锁 / 传递解锁 / 总计 | 三个数字 |
| 解锁了哪些 | 列出被解锁条目的 §20 任务 ID |

### 步骤 4 · 单独标出「零成本签字」

有些决策的**当前代码实况已经等同于某个选项**(N2 审计里标「偏差(方案现状已过时)」的那类)。
这类只要用户确认「就按现状冻结」即可,不需要任何返工。**单独成节列出**,这是最便宜的解锁。

⚠️ **但不得把「代码已这样实现」直接写成「已签字」**。方案 §0.1 明写「G0 不使用『未提异议即冻结』」。
实况只是让签字变便宜,不代表签过。CLAUDE.md v1.52 已把 `INNER-DEMON-CULTIVATION-01` 落进生产,
而它在 registry 里仍是 `PROPOSED` —— 这就是反例,写菜单时按此口径处理。

## 硬约束

### 禁代拍(本单最重要的一条)

**不得推荐用户选哪个选项。** 不写「建议选 A」「推荐方案 B」「更合理的是」。
只呈现:问题是什么、有哪些选项、每个选项解锁多少、拍板前需要看什么。
排序依据只能是**解锁力这个客观量**,不是你对哪个方案更好的判断。

唯一例外:步骤 4 的「零成本签字」节可以指出「按现状冻结无返工成本」,
因为这是成本陈述不是方案偏好;但仍不得说「所以应该这么签」。
