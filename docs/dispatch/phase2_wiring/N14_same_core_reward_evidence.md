## 方法

### 步骤 1 · 先定「7 组到底是哪 7 组」

从 N2 `L56` 现取,逐组写进报告的第一张表:组号 / 原文断言 / 当前为何无法判定。
**如果现取发现不是 7 组,以现取为准并在报告开头写明差异** —— 不要为了凑 7 而拆分或合并。

### 步骤 2 · 固定 seed 的模式矩阵

对每组断言,构造一个**固定 seed** 的对照:同一关卡、同一角色快照,分别走
`manual` / 前台 `bot` / `headless` / `sweep` 四条路径,比对:

- 每 tick 的战斗状态 hash(或等价的确定性摘要)
- 最终结算的掉落 profile(重复掉落也要计入)

随机源必须走 `rngProvider` 注入,**不要新接 `dart:math Random` 签名的 service**
(会绕开 override,项目 CLAUDE.md §9.1 明列)。

### 步骤 3 · 逐组给结论

每组必须落到 `PASS` 或 `FAIL` 之一,**禁止再出现「无法判定」**。
如果某组确实做不出判定,那说明缺的是能力不是证据 —— 走 `[BLOCKED]` 出口,说明缺什么。

## 关键:红了怎么办(本单最容易出假绿的地方)

如果某组断言的实测结果是 **FAIL**(四种模式确实不同核):

1. **不要**把这条红测试提交到分支上 —— 那会让 Gate 的 `full_test` 变红,
   把一个**有价值的发现**变成一个**挡路的红**。
2. **也不要**为了让它绿而放宽断言、改生产代码、或改成只测通过的那部分 —— 那是假绿,
   是本项目最高发的失败模式。
3. **正确做法**:
   - 测试留在分支上,但加显式 `skip:`,skip 的理由字符串里写清
     「本断言实测 FAIL,证据见 `docs/audit/<报告>.md` 第 N 组」
   - 报告里那一组标 `FAIL`,贴**完整实测输出**(命令 + 退出码 + 差异摘要)
   - tip commit 打 `[BLOCKED]`,因为「四模式不同核」属于需要用户决定怎么处理的发现

只有 7 组**全部 PASS** 时才打 `[READY]`。
