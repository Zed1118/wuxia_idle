也就是说:现有测试证明「解析逻辑按预期工作」,但**没有任何证据表明它在真实全仓上判得准**。
Mock 掉 git 调用意味着「这个路径到底存不存在」这个最关键的判断从没被真实验证过。

**本单要产出的就是那个缺失的证据:真实语料上的 precision / recall。**

## 二、本单要做的事

### 1. 抽样(50-100 条)
- 从扫描器输出的**全部**条目里抽 50-100 条做人工标注样本
- **分层抽样,不要只抽一类**:「判为死链」和「判为存活」两类**都要抽**,
  各占相当比例。只抽死链算不出 recall,只抽存活算不出 precision
- 「ignored」类也抽几条,确认忽略规则没误伤
- 抽样方法要可复现:固定种子或直接记录抽中的条目清单

### 2. 逐条独立标注
对每条样本,**不看扫描器的判定**,自己独立判断这个引用是死是活。判断依据:
- 目标文件是否真实存在(`ls` / `git ls-files` 现查)
- 是否被 gitignore(`git check-ignore`)
- 锚点型引用(`file.md#section`)要看该 section 是否真的在目标文件里
- 相对路径要从**引用所在文件的目录**解析,不是从仓库根

⚠ 这一步是全单的价值所在。**不许拿扫描器的输出当标注答案**——那样算出来的
precision/recall 恒为 100%,是自证循环,等于什么都没验。

### 3. 算 precision / recall
- 以「死链」为正类:
  - TP = 扫描器判死链 且 你标死链
  - FP = 扫描器判死链 但 你标存活
  - FN = 扫描器判存活 但 你标死链
  - TN = 两边都判存活
- precision = TP/(TP+FP),recall = TP/(TP+FN)
- **每一个 FP 和 FN 都要逐条写出来**:条目原文、扫描器判什么、你判什么、根因是什么
  (FP/FN 的根因分析比那两个百分数值钱得多)

### 4. 交付报告
