# 挂机武侠 · 全局内容与视觉质量审查及下一阶段改进计划

> 审查日期：2026-07-25  
> 审查性质：全局审查，不仅针对最近提交  
> 目标：作为 1.0 长线打磨期下一阶段的主要工作计划  
> 边界：只提升既有内容的视觉呈现、信息层级、资产一致性、桌面适配与验收能力；不借视觉改造新增玩法，不触碰 `docs/spec/rejected_task_registry.md` 中已否或暂缓方向，不改数值与经济规则。
>
> **执行边界补充（用户确认）**：既有视觉风格、页面结构、信息顺序与交互路径均视为已确认，不做重设计。本文中双栏、页签、固定宽度调整等结构候选仅作为审查记录，不进入本轮实现；实际修复只处理溢出、对比、间距、状态、资源误用、响应式与无障碍。

## 1. 结论先行

当前版本已经形成了明确的“写实武侠 + 水墨宣纸”产品身份，主菜单、主线关卡、闭关地图、桃花岛、部分装备详情和关键战斗反馈，已经明显高于普通功能型独立游戏 UI。问题不在于缺少好页面，而在于完成度分布不均：

- 核心页面已经接近成品；
- 长尾系统仍保留较多“开发工具面板”气质；
- 战斗素材虽然数量充足，但人物角色、尺寸、透视和辨识度仍未彻底统一；
- 浅色宣纸与深色全局 Theme 的继承边界不可靠，仍能产生严重低对比；
- 桌面宽屏下既有固定宽度过窄，也有一次性塞入过多信息的问题；
- 字体、字号、颜色和间距主要靠页面逐处硬写，后续继续扩内容会反复产生漂移；
- 视觉验收基建很强，但启动页、存档页、设置页、纯净主菜单等真实高频界面仍未纳入自动视觉路由。

综合判断：

- **内容与系统呈现：7.8 / 10**
- **视觉美术与氛围：7.7 / 10**
- **界面一致性与完成度：6.7 / 10**
- **战斗可读性：6.4 / 10**
- **桌面响应式与可访问性：6.2 / 10**
- **视觉工程与验收基础：8.2 / 10**
- **全局综合评分：7.2 / 10**

这不是推倒重做项目。下一阶段应以“收口”为主：修硬伤、立系统、清素材、分批迁移、补验收。完成本计划后，合理目标是把综合质量提升到 **8.5 / 10 左右**，并让后续新增章节和系统不再继续制造视觉债。

## 4. 高优先级问题

下列问题建议在任何大范围“美化”前先修。它们不是审美偏好，而是已经影响可读性、布局正确性或正式感。

### P1-01 章节总览的 16 章横向路引整排溢出

**现象**

- `chapter_list` 在 1280×720 下，16 个章节面板同时被塞进 1040 宽的 Row；
- 每个章节面板均出现 Flutter `RIGHT OVERFLOWED BY 5.9 PIXELS` 调试条；
- 章节标题、状态和节点被压成极窄竖条，可读性严重下降。

**根因**

- `chapter_list_screen.dart` 只以 `constraints.maxWidth < 1040` 判断是否进入横向滚动；
- 当宽度略大于 1040 时，逻辑转为 16 个 `Expanded`，却没有按章节数量计算最小卡宽；
- 16 章扩容后，旧阈值已经失效。

**修复方向**

- 用“条目数量 × 最小卡宽 + connector”计算是否必须滚动；
- 16 章模式默认采用横向卷轴或分页式章节路引；
- 保证每章面板的标题、状态、5 个关卡节点均有最低可读宽度；
- 不新增“章节回顾入口”，只修现有章节总览。

**验收**

- 1280×720、1440×900、1920×1080 均无 overflow；
- 第 1、9、10、11、16 章长短标题均不出现单字残缺；
- 键盘、滚轮、触控板可水平移动；
- 当前章首次出现时自动可见；
- 增加 16 章数据量的 widget 回归测试。

### P1-02 设置面板浅宣纸底出现大面积白字

**现象**

- 真实应用设置面板中，音频、战斗舒适性、窗口与显示、存档与系统等大量正文为白色；
- 白字落在浅黄色宣纸上，对比严重不足；
- disabled 按钮和说明文字更接近不可读；
- 1366×768 下内容依赖窄长滚动，固定底部“关闭”区进一步压缩内容。

**根因**

- `PaperDialog` 仅用 `DefaultTextStyle.merge` 设置深墨正文；
- `ListTile`、`SwitchListTile`、Dropdown、Slider 等 Material 组件优先读取全局 dark Theme 的组件/文字颜色，不完全继承 `DefaultTextStyle`；
- 设置面板正好大量使用这些组件，因此浅色容器与深色 Theme 发生冲突。

**修复方向**

- 为浅色表面定义完整的局部 `ColorScheme`、`TextTheme`、`ListTileTheme`、`SwitchTheme`、`SliderTheme`、`DropdownMenuTheme` 和 disabled 状态；
- 将其封装为 `PaperSurfaceTheme`，由 `PaperDialog`、浅色全屏页统一消费；
- 设置面板在桌面宽度足够时改为 2 列或分组页签，避免 360 宽长卷轴；
- 不改变设置功能，只改善呈现。

**验收**

- 正文对比度不低于 4.5:1，较大标题不低于 3:1；
- 启用、禁用、选中、悬停、焦点状态均可辨；
- 1280×720 首屏能看完音频和舒适性两组，或明确表现为分组导航；
- 关闭按钮不遮挡内容；
- 为 `PaperDialog + ListTile/SwitchListTile` 增加渲染颜色测试；
- 新增 `settings` 视觉路由。

### P1-03 战斗人物素材角色混用，直接破坏正式感

**现象**

- 某些战斗路由中，完整全身立绘与大头肖像同场出现；
- 方形/半身素材被放大后像一张巨大照片贴在战场上；
- 同一位老者可在左右两队同时出现，玩家/敌人身份辨识弱；
- 部分人物尺度、脚底高度、透视和光源不一致；
- 角色名在半透明墨牌上仍偏暗，战场浅雾区可读性不足。

**根因**

- `_resolvedStageIconPath` 对已注册角色使用专用 standee，对未注册素材继续回退到原 `iconPath`；
- 旧敌人的 fallback 路径被测试明确允许使用 `BoxFit.cover + ShaderMask`，但“允许降级”不等于正式路由观感合格；
- 资产门禁检查“文件存在”，尚未检查“资产角色正确”。

**修复方向**

- 把 portrait、battle standee、codex portrait、equipment icon、equipment detail 定义为明确资产角色；
- 正式战斗路由禁止把 portrait 直接当 standee；
- 为高曝光角色补专用透明全身立绘或改用统一剪影降级；
- 建立左右队伍的非颜色单一辨识：站位、边框纹样、朝向或墨色温度；
- 重做战斗状态牌的文字对比与底部锚点。

**验收**

- 116 路由中所有正式战斗帧不再出现方形照片式人物；
- 同帧不得出现无法区分的同脸敌我，镜像剧情除外；
- 所有 standee 满足透明通道、最小尺寸、合理长宽比和脚底标定；
- 名字、HP、内力在所有战场背景上均可读；
- 增加资产角色审计和正式路由 fallback 计数，目标为 0。

### P1-04 启动、存档、设置等真实高频界面未进入自动视觉回归

**现象**

- `main_menu` 路由固定带归来弹层，无法检查纯净主菜单；
- 启动页、存档选择、设置面板不在 116 路由中；
- 设置面板低对比因此长期绕过现有 `paper text contrast` 门禁；
- 存档页 380 固定宽在宽屏下过小，也未被视觉套件发现。

**修复方向**

- 新增真实视觉路由：
  - `splash`;
  - `save_select_empty`;
  - `save_select_filled`;
  - `main_menu_clean`;
  - `main_menu_offline_recap`;
  - `settings_top`;
  - `settings_bottom`;
  - `settings_disabled_states`;
- 明确 debug harness 是否包含生产 chrome，报告中标记 `production-shell` 与 `component-only`。

**验收**

- 所有一级入口和设置页均至少有一条生产 shell 路由；
- 视觉报告能区分正式页、动态 overlay、调试画廊；
- 新路由进入 1280 与 1440 smoke。

## 5. 主要系统性问题

### P2-01 字体系统几乎没有语义化，Windows 发布存在外观漂移风险

**现状**

- 没有正式字体资源和跨平台 fallback 方案；
- 782 处字号、915 处 TextStyle 分散硬写；
- 页面几乎不使用全局 `textTheme`；
- 战斗区局部建立了 `BattleTypography`，但未扩展到全产品。

**风险**

- macOS 与 Windows 的中文系统字体、字宽、字重和标点位置不同；
- 当前许多布局依赖精确字宽，Windows 125%/150% 缩放时更容易截断；
- 全局视觉难以仅靠逐屏调字号收口。

**改进**

- 建立 7 个语义字阶：display、screen title、section title、body、secondary、label、micro；
- 每个字阶定义字号、行高、字重、字距、颜色用途；
- 选择有明确授权的跨平台中文字体，或制定严格的 Windows/macOS fallback 组合；
- 若嵌入完整 CJK 字体体积过大，先评估子集化和字体许可；
- 保留题字/印章为装饰字体，正文不得使用难读书法字。

### P2-02 两套视觉语言并存：宣纸成品页 vs 深色工具面板

**表现较成熟**

- 主线、闭关、桃花岛、装备详情、结算卷宗。

**表现偏工具化**

- 祖师创建；
- 门派谱与门人详情；
- 奇遇录列表；
- 技能库；
- 江湖远行；
- 断魂庄整备、关间整备、论功行赏；
- 部分资源与图鉴页面。

**问题**

- 同一产品中有的页面像古籍册页，有的像后台管理工具；
- 深色列表常由等高矩形、细边框、小字和大量空白构成；
- 长线系统内容越多，这种差异越明显。

**改进**

- 不要求所有页面都铺满宣纸；
- 统一“深色战备页”模板：
  - 顶栏；
  - 主任务区；
  - 次级信息区；
  - 选择态；
  - 主要动作；
  - 空状态；
- 为档案、图鉴、整备、远行分别建立 3 类模板，减少每页自由发挥。

### P2-03 宽屏空间利用不稳定

**过窄**

- 存档卡固定 380；
- 技能库主体约占屏幕 40%–50%；
- 藏卷阁、兵器谱详情、离线归来卡等大量内容固定在窄列；
- 角色面板上半部左侧有内容，右侧大面积空纸。

**过密**

- 章节 16 项一次塞满；
- 物品仓库筛选区占据近半首屏；
- 战斗底部指令台信息密度高；
- 主菜单在 1366×768 下需要滚动才能看完二级系统。

**改进**

- 建立桌面内容宽度级别：
  - compact：420–560；
  - reading：680–860；
  - management：960–1160；
  - full-stage：全宽；
- compact 只用于真正的短弹层；
- 列表和档案页宽屏优先双栏或“目录 + 详情”；
- 过滤器默认只显示高频条件，其他条件折叠到高级筛选，不删除任何现有过滤能力。

### P2-04 战斗底部 HUD 与战场画面竞争

**现象**

- 指令台占屏幕高度约四分之一；
- 技能为空时仍保留大面积空纸卡；
- 技能不可用时多张卡重复显示同一“真气不足”，形成噪声；
- 顶栏、状态牌、人物、数字、技能卡和行囊同时争夺注意力。

**改进**

- 定义战斗注意力优先级：
  1. 当前动作与关键反馈；
  2. 敌我生存状态；
  3. 可干预技能；
  4. 战备行囊；
  5. 日志和次要信息；
- 空槽收缩为占位纹样，不保持完整卡片重量；
- 同类不可用原因可在指令区汇总一次，卡内只保留符号或短标签；
- 快进、暂停、日志等工具按钮降低静态视觉权重；
- 不增加 Boss 预兆图标，不触碰已否方向。

### P2-05 战斗敌我与流派辨识仍弱于 GDD 目标

GDD 要求“不看伤害数字也能判断当前是谁克谁”。目前：

- 敌我 HP 都主要使用红色；
- 流派信息集中在底部列表或小色点；
- 人物色调经过统一融合后，角色个性与阵营差异进一步降低；
- 同脸或近似服装会加剧混淆。

**改进**

- 不依赖红/绿二色，使用边框纹样、队伍朝向、名牌形制或墨色冷暖区分敌我；
- 流派保留颜色，但增加图形/纹理编码；
- 关键克制只在触发瞬间强化，不让常态画面堆满效果；
- 保持“美术克制、反馈强烈”的 GDD 原则。

### P2-06 装备详情素材规格不一致

**证据**

- 83 个普通装备图均有对应 detail 文件；
- 3 组 detail 与 icon 完全相同；
- detail 画廊中存在：
  - 透明暗色物体在深背景上几乎消失；
  - 白底书画与透明抠图混排；
  - 物体尺度和留白差异过大；
  - 部分图带大量书法，是否为可读文字没有统一规则。

**改进**

- 详情图统一 1:1 画布、主体占比、视觉重心和安全区；
- detail 画廊自身改为宣纸底预览，避免误判透明暗色物件；
- 3 组重复图补专用详情画面；
- 新增 perceptual duplicate 审计，允许明确登记的例外。

### P2-07 场景图比例仍有少量离群

场景主规格为 1456×816，但以下素材不同：

- 3 张 1672×941；
- 1 张 `battle_cliffwaterfall.png` 为 1024×1024。

这不一定直接是 bug，但在 `BoxFit.cover` 下会产生不同裁切，尤其对文字、人物和地标位置不利。

**改进**

- 为场景图登记 focus point；
- 场景不强制重出时，至少明确 16:9 安全裁切区域；
- 视觉路由覆盖每个离群场景的 1280、1440；
- 新场景默认统一 16:9。

### P2-08 书法题字与印章的伪文字边界尚未拍板

当前不少场景和装备图包含书法、印章或类似文字的纹样。它们能强化武侠气质，但也可能：

- 出现不可识别或似是而非的 AI 字；
- 与 UI 真文字争夺注意力；
- 在国际化、无障碍和品牌一致性上形成风险。

**建议拍板**

- 保留“经过人工确认、确实可读、与内容一致”的书法；
- 保留纯抽象纹样，但不得让玩家误以为应当阅读；
- 禁止似汉字但无法辨认的 AI 伪文字；
- 印章需使用受控字形或明确抽象化；
- 拍板后对 `assets/scenes`、`assets/equipment` 做一次全量分类，而不是边做新章节边零散判断。

此项对应 `BACKLOG.md` §一 #11，必须先完成设计决策再批量改图。

### P2-09 颜色 token 有基础，但仍未成为唯一来源

- 当前自动审计仍有 222 个颜色问题；
- 其中大部分是历史硬编码，不代表每处视觉错误；
- 真正风险是相同语义在不同页面形成不同米黄、墨黑、暗红和 disabled 透明度。

**改进**

- 颜色 token 按“语义”而不是按“颜色名称”组织：
  - light surface text；
  - dark surface text；
  - selected；
  - disabled；
  - destructive；
  - success；
  - warning；
  - team left/right；
  - school；
  - rarity；
- 背景场景调色可保留局部颜色，不要求全部迁入 UI token；
- 先迁共用组件，再迁高频屏，避免一次性 200 处机械替换。

### P2-10 信息层级存在“数据都在，但第一眼重点不明确”

典型页面：

- 物品仓库：筛选、状态、排序、总览同时高权重；
- 资源总览：资源卡片多，但“当前最值得关注”与普通库存层级接近；
- 远行/断魂庄：标题、队员、路线、补给、动作均使用相似深色框；
- 角色面板：身份、属性、装备、成长的主次因大面积留白而削弱。

**改进**

- 每页只允许一个视觉主任务；
- 次要说明进入弱化层，不与按钮、数值争夺；
- 数字统一为“核心值 / 次值 / 注释值”三级；
- 空状态不保留完整数据密度；
- 不新增战败原因诊断、目标追踪等已否功能。

## 6. 细节瑕疵清单

这些问题单独看不致命，但会共同决定“像完成品还是像仍在开发”。

### 6.1 启动与存档

- 启动页画面优秀，但标题与“轻触继续”位于背景低对比区域，字号也偏小；
- 存档选择纯深底、380 宽卡片，在 1366 宽窗口中显得像临时工具；
- 卡片信息较全，但标题、标签、日期的字阶差距小；
- 编辑与删除仅为小图标，危险操作视觉区分依赖颜色。

### 6.2 顶栏与导航

- 纸质顶栏、深色战斗顶栏、普通深色 AppBar 的高度和标题字阶不完全一致；
- 返回、主页、帮助、印章图标的视觉重量不均；
- 某些页面标题金色过亮，容易压过内容；
- `Boss`、`Lv`、`slot`、版本号等中英混排口径不统一。

### 6.3 主菜单

- 整体表现强，但文字偏小，1366×768 下二级系统需要滚动；
- 锁定卡和可用卡主要依赖降低亮度，低视力用户不易区分；
- 调试分区与正式内容同屏，开发期合理，release 必须确认完全隐藏；
- `main_menu` 自动路由只拍归来弹层，缺少纯净状态。

### 6.4 角色与编成

- 角色面板上半部右侧空纸过多；
- 编成屏的三名角色使用首字方块而不是已有头像或统一剪影，原型感较强；
- “主角/弟子/位置/装备”之间的结构联系主要靠文字，没有足够的空间分组；
- 部分测试状态数值为 0，会削弱截图的可信度，视觉 fixture 应更接近真实存档。

### 6.5 章节、关卡与塔

- 章节路引已出现实际 overflow；
- 长章节名和双 Boss 章需要专门检查，不应只测第一章；
- 塔路线在 1280 下纵向卡较大，首屏可见层数偏少；
- 当前层、最高层、可挑战层的边框差异在低亮度屏幕上偏弱。

### 6.6 仓库与装备

- 仓库筛选区高度过大，首屏主内容被推到下半部；
- 品阶、部位、流派、状态全展开时，用户要先读一整面控件墙；
- 卡内核心属性会省略，截断位置不总能保留最关键数字；
- 装备详情的强化等级 `+12` 与速度同行但缺少明确标签，容易被理解为速度附加值；
- “默契？”中的帮助符号和标题贴得过近；
- 部分详情页右栏下半部空白较多。

### 6.7 商店与资源

- 1280 单列时每行过宽，图标和说明集中在左侧，横向空间利用弱；
- 1440 双列明显更合理，应把响应式断点和卡宽模式固化；
- 价格、持有量、来源、用途的层级仍可再拉开；
- 资源总览的纸卡与深色背景关系清楚，但左侧主体偏窄。

### 6.8 图鉴与档案

- 技能库在宽屏下仍是窄列，右侧形成大量黑色空白；
- 兵器谱详情只有两张纸卡，缺少与列表页一致的视觉重心；
- 门派谱和门人详情偏普通后台列表；
- 藏卷阁是窄列卡片集合，作为档案 Hub 尚缺“藏卷”空间感；
- 调试画廊中的英文 ID 不计入正式 UI 问题，但暴露了资产不一致。

### 6.9 桃花岛与闭关

- 两者属于当前强项；
- 桃花岛建筑弹层在 1280 下占据大部分屏幕，1440 下比例更舒适；
- 弹层内容区密度高，按钮和材料需求可再分层；
- 闭关卡片上部分暗金/黄色文字落在浅纸区域，对比略弱；
- 场景题字与印章需纳入伪文字拍板。

### 6.10 远行与断魂庄

- 功能信息完整，但深色矩形列表过多；
- 队员、路线、补给和关卡层级相近；
- 论功行赏的三张奖励卡有结构，但整体页面顶部和右侧留白大；
- 战败页信息较少，空白是否表达沉重感需要有意控制，而不能只是内容不足。

### 6.11 结算、弹层与动态题字

- 动态题字截图看起来“空”，其中一部分是因为本来只显示 0.5–1 秒，不能用静态填满原则误修；
- 真正需要检查的是出现位置、停留时长、背景适配和与人物/数值的遮挡；
- 离线归来卡固定 420 宽，信息较长时形成窄长阅读；
- 技能领悟、招式获得等小卡在宽屏中比例偏小；
- 胜负卷宗整体成熟，但不同结算页宽度和按钮位置仍可统一。

### 6.12 文案与术语

- 玩家可见文案已高度集中到 `UiStrings`，这是优点；
- 仍有 `Boss`、`Lv`、`slot`、`skill`、版本号等中英混排；
- 不要求全部中文化，但需制定术语表：
  - 正式世界观词；
  - 数值缩写；
  - 开发调试词；
  - 存档/系统技术词；
- 同一界面避免“小时/时辰”“周目/轮回”等语义相近词并存；
- 归来卡、战斗禁用状态、关卡目标等存在重复表达，应以“先结论、后明细”压缩；
- 本次未对 587 个叙事/lore/event 文件逐段做文学编辑，下一阶段需设独立内容编辑批，不能把视觉抽样等同于全文校对。

## 8. 建议的批次切法

为了减少多人/多会话冲突，每批只跨一个视觉基础层和一组页面。

| 批次 | 内容 | 主要文件域 | 风险 |
|---|---|---|---|
| A | 章节 overflow + 设置浅底 Theme + 新视觉路由 | mainline/settings/debug route | 低至中 |
| B | typography/surface tokens + 通用组件 | shared/theme/shared/widgets | 中 |
| C | 战斗人物角色与状态牌 | battle/assets/visual tests | 中至高 |
| D | 启动、存档、主菜单、角色、编成 | save/main_menu/character/lineup | 中 |
| E | 主线、塔、仓库、装备、商店、闭关、桃花岛 | high-frequency features | 中 |
| F | 图鉴、档案、远行、断魂庄等长尾 | codex/baike/expedition/gauntlet | 中 |
| G | 内容编辑 + 全局双视口 + Windows 预备验收 | strings/data/visual QA | 中 |

每批都遵守：

- 改前保存对应视觉路由基线；
- 改中跑 targeted test；
- 改后跑 `flutter analyze`；
- UI 密集批必跑 1280、1440；
- 批末才做一次全量测试；
- 不把临时截图和 capture 目录提交到 git；
- 更新 `PROGRESS.md` 时区分已完成、已验证、已知风险、下批建议。

## 9. 量化验收标准

### 9.1 布局

- 1280×720：0 overflow、0 关键内容裁切；
- 1440×900：不只是拉伸，应有效利用新增空间；
- 长标题、最大数值、锁定标签均需测试；
- compact 弹层宽度不超过其内容需要，管理页不得只占屏幕 30%。

### 9.2 可读性

- 正文对比度 ≥ 4.5:1；
- 大字/粗标题 ≥ 3:1；
- disabled 状态仍可读，但不得与 enabled 混淆；
- 实景图上的文字必须有 scrim、描影或安全留白；
- 720p 下正文目标不低于 13 logical px，micro 文字只用于非关键补充。

### 9.3 战斗

- 人物资产角色错误：0；
- 正式路由 fallback：0；
- 同脸敌我：0，剧情镜像除外；
- 名字、HP、内力不可被人物或相邻角色遮挡；
- 关键反馈在 1 秒内可识别；
- 空技能槽不占用与满槽同等视觉重量。

### 9.4 素材

- 战斗 standee 必须有 alpha；
- 新 standee 默认竖幅，长宽比和脚底锚点进入门禁；
- 场景默认 16:9，离群图必须登记 focus point；
- detail/icon 完全重复需登记或修复；
- AI 伪文字 0；
- 所有人工可读题字内容正确。

### 9.5 一致性

- 同类页面使用同一模板；
- 同一语义只使用一套字阶、颜色、边框和状态表达；
- 正式 UI 中的中英混排符合术语表；
- 新页面不新增未登记硬编码高饱和色；
- 新页面优先使用语义 typography，而非直接写 `fontSize`。

## 10. 不应做的事情

- 不做全仓一次性机械换色；
- 不把所有深色页都改成宣纸页；
- 不为了填满宽屏而堆新信息；
- 不把动态题字按静态页面原则强行做大；
- 不用更艳的金色、红色来解决层级；
- 不用同一张肖像兼任头像、战斗立绘和详情图；
- 不借视觉改造新增已否功能；
- 不在 macOS 看起来正确后就认为 Windows 字体和缩放也正确；
- 不用像素 diff 替代人工视觉判断。

## 13. 最终判断

《挂机武侠》的视觉上限已经被少数强页面证明，下一阶段无需再追求“再做几个漂亮页面”。真正能显著提升整体质感的是：

1. 让浅色与深色表面真正成为可靠系统；
2. 让字体和宽屏布局不再依赖页面手工调参；
3. 让战斗人物全部符合资产角色和透视规范；
4. 让长尾系统从开发面板升级为同一产品的正式页面；
5. 让隐藏高频界面和 Windows 发布条件进入视觉门禁。

这应当成为下一阶段的主线工作，优先级高于继续横向增加新系统。
