# F2「wait=80 冻结 vs wait=85 濒死」机制查明(销 BACKLOG 二#9)

**日期**:2026-08-05 夜班 · **基线**:`0bb16d37` · **零生产改动,纯代码取证**
**前作**:`docs/audit/f2_battle_action_frames_2026-07-30.md` §四留的「未解释」项。

## 机制定论(代码证据齐)

`mainline_first_clear_battle_auto` 的外部 Timer(2.2s,`visual_route_host.dart` `_startAutoStep`)每次调 `BattleNotifier.step()` → `_strategy.stepOne`(`battle_providers.dart:186-193`)。**stepOne 是双形态状态机**(`battle_state.dart:757-760` 行动队列字段注释):

1. **tick 边界(行动队列空)**:推进全员 AP/CD + 把跨阈者排序入队,**不结算任何 actor**;
2. **队列非空**:弹出队首**一个** actor 结算。

顶栏节拍号只在 tick 边界 +1;**弹 actor 的 step 不涨拍号**。由此三个现象全部闭环:

- **前 8 拍战场冻结**:首通调优速度下全员 AP 从 0 蓄到阈值约需 8 个 tick,期间每步都是「空转的 tick 边界」——拍号涨、战场零变化(07-30 批 beat1↔7 差分 0 像素的直接原因);
- **同为拍 8,wait=80 冻结而 wait=85 濒死**:第 8 tick 全员几乎同时跨阈(速度相近),一次性入队 4 个 actor;其后 2-3 个 step(2.2s×2.27≈5s)逐个弹出结算——**拍号钉在 8 不动,战斗剧变**;
- **伤害账「对不上」**:8700→420 需 ≈8280 伤,战报条只显最近 2 条(二弟子 833 暴 + 大弟子 3790 暴),第三个已结算 actor(祖师,~3657)被挤出显示——账实际闭合,是战报条截断造成的错觉。

## 对取帧配方的推论(补 07-30 判据)

- 「节拍号」不是行动进度刻度:同一拍号内可以有 0~4 个行动被结算。精确定帧看**战报条区均亮**(07-30 判据)仍是对的;若要卡「第 N 个行动」,应按 `wait ≈ 60+setup抖动 + 8×2.2 + N×2.2` 估算后**以战报内容回读确认**。
- 想缩短冻结段:调小 `autoStepInitialDelay` 不解决(那是 setup 缓冲);真正的 warmup 是 AP 蓄条 8 tick,如需快进可在 route 侧先空跑 8 次 `step()` 再起 Timer(未实装,留需要时做)。
