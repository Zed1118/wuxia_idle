## 为什么做

此前主线立绘的验收只到**素材层**（尺寸 / 四角 alpha / 脚底 fraction / 逐图目检原图），
真机战斗屏目检长期挂在账上——PROGRESS 里 Ch16「立绘真机战斗屏未目检」、
Ch17/Ch18「两章立绘均未真机战斗屏目检」、Ch20/Ch21 同样在账。

**这个空档不是形式主义**：本夜第一件事就是在 Ch21 逮到 `jueding_lunjian_houren`
**左脚整只悬空 164px**，而素材层九判据全绿（它只验 alpha 包围盒**底沿**，单脚悬空不改底沿）。

## 方法

```
visual_capture.sh --route battle_audit_stage_<NN>_<MM> --resolutions 1280x720 --background
```

真 `ScenarioLauncher` + 真 stage 背景 + `startPaused` 冻结首帧；
1280×720 逻辑 = 2560×1440 物理。判据取各章 `build/dispatch/ch*_art_*` 派单书原文题眼。

复核走两层：
1. **接触印相表**批量过眼（每关裁敌立绘带 + 脚下地面）——抓悬空 / 裁切 / 道具错 / 兵器错这类粗缺陷；
2. **逐张放大**核验题眼——用于当章判据最细的那几张。

## 顺带解掉 battle-ui 遗留 F2（原判「工具不支持」）

阶段 5 把 F2 记作「所有 visual route 冻结静态帧，`--wait` 不推进战斗，全仓无特效 route」，
据此扣 1 分并判定不可做。**本轮实测证伪**：

`mainline_first_clear_battle_auto` 路由本就带 `autoStep: true`，但
**`autoStepInitialDelay` 是 60 秒**——当初试的 `--wait 14/17/20/23` 全都没等到自动推进开始，
所以永远停在节拍 0。

改用长 wait 实测：

| `--wait` | 实际节拍 | 帧内容 |
|---|---|---|
| 75 | **节拍 6** | 战斗中 |
| 95 | **节拍 11** | 二弟子「飘叶手」833 伤（暴击）/ 大弟子「快剑」3790 伤（暴击）/ 敌 420/8700 濒死 / 技能牌「破招」态 |

两帧差异 **26.5%**，战斗确实在推进。推进速率约 **4s/节拍**，故配方 =
**`--wait ≈ 60 + 4×N` 落到第 N 拍**。

> **2026-07-30 订正（`docs/audit/f2_battle_action_frames_2026-07-30.md`）**：上面这个公式**不要照抄**。
> 底层定时器实为 **2.2s**（`visual_route_host.dart:1464`），4s 是拿两点相除得来的、其中一点落在冻结段；
> 端到端实测约 3.4s/拍且每次启动开销有秒级抖动。更要紧的是**前 8 拍战场是冻结的**
> （beat 1 与 beat 7 立绘带逐像素差异为 0），故「任意拍都能拿到动作帧」不成立。
> 改用可判读判据：战报条区均亮由 ~89 掉到 ~30 = 该帧是动作帧。

**结论：F2 的阻塞前提不成立，那 1 分是可取的**（能否精确截到某一瞬的粒子/闪白仍看时序运气，
但「route 冻结、wait 无效」这个判据本身是错的）。
